## 🧪 테스트 설계

### 설계 방식 — 메뉴 트리 기반

원티드의 페이지·메뉴 구조를 트리로 전개하고, **각 메뉴 항목마다 TC를 할당**하는 방식으로 설계했습니다.
기능 단위로 빠짐없이 훑기 위한 방법으로, TTA에서 GS 인증 시험을 수행할 때 쓰던 방식을 가져왔습니다.

```
공통 요소    헤더(이동·검색·알림·프로필) / 푸터
메인 페이지   숏컷 메뉴 / 캐러셀 슬라이더
채용 페이지   필터(직군·지역·채용조건·초기화) / 채용 리스트(이동·북마크·렌더링)
채용 상세    공고 정보 / 회사 위치 지도 / 지원 프로세스
검색 페이지   직접 입력 / 최근 검색어 / 연관 검색어 / 인기 검색어 / 결과
사용자 페이지  프로필 / 내 활동 / 게시글 / 설정 / 로그아웃
```

### 우선순위와 자동화 구분

| 구분 | 건수 | 기준 |
|---|---|---|
| 자동화 | 22 | 반복 실행 가치가 있고, 결과를 기계적으로 판정할 수 있는 것 |
| 수동 | 11 | 로그인이 필요하거나, 내용의 적절성을 사람이 판단해야 하는 것 |

우선순위는 P0(핵심 플로우) / P1(주요 기능) / P2(참고)로 나눴습니다.

> TC 설계서는 별도 스프레드시트로 관리합니다.
> 이 README는 요약만 담고, TC별 상세(사전 조건·시나리오·예상 결과)는 설계서를 원본으로 합니다.

```
│   │   ├── main_page.py

│   └── conftest.py                # 드라이버 fixture
├── requirements.txt
└── .github/workflows/test.yaml    # GitHub Actions
```

### 설계 원칙

- **POM 패턴** — 페이지별 로케이터와 액션을 캡슐화
- **컴포넌트 단위 분리** — 헤더는 모든 페이지에 걸쳐 있으므로 페이지가 아닌 컴포넌트로 분리
- **데이터 속성 기반 Locator** — 해시 클래스명 대신 `data-gnb-kind` 등을 사용해 마크업 변경에 덜 민감하게
- **Explicit Wait** — `WebDriverWait` + `expected_conditions`
- **환경 분리** — URL·헤드리스 여부·대기시간을 `.env`로 분리
- **스킵 사유를 코드에 남김** — `@pytest.mark.skip(reason=...)`으로 왜 건너뛰는지 기록

## 🚫 자동화하지 않은 것과 그 이유

**실제 운영 서비스를 대상으로 하면서 생긴 제약입니다. 이 프로젝트에서 가장 많이 고민한 부분입니다.**

### 1. 로그인이 필요한 영역 — 33건 중 9건

테스트 계정을 만들 수 없었습니다. 이미 가입한 명의로 재가입이 불가능했기 때문입니다.
**전부 포기하지 않고, 어디까지 검증 가능한지를 기준으로 세 갈래로 나눴습니다.**

| 대응 | 대상 | 내용 |
|---|---|---|
| 수동 전환 | 프로필 이동 · 사용자 페이지 5종(메뉴 이동 · 소개 작성 · 지원 현황 · 게시글 · 로그아웃) | 직접 로그인해 수동 수행하고 결과를 설계서에 기록 |
| 스크립트만 작성 | 최근 검색어 | 코드에 남기고 `skip` — 사유를 reason에 기록 |
| 실행하지 않기로 | 지원하기 | 실제 지원이 발생하므로 수동에서도 실행하지 않음. 설계 의도만 설계서에 기록 |
| 부분 검증 | 북마크 | 기능 전체는 못 보더라도 진입 지점의 피드백까지는 확인 |

```python
@pytest.mark.skip(reason="로그인 필요 (테스트 계정 생성 불가, 이미 가입한 명의로 재가입 불가능)")
def test_recent_searches(browser, base_url):
```

> "못 한다"로 끝내지 않고 **어디까지 검증 가능한지를 기준으로 갈랐습니다.**

### 2. 검증할 수 없는 것

**인기 검색어 (TC_012)** — 순위는 동적 데이터라 기대값을 고정할 수 없습니다.
영역이 존재하는지, 항목이 1개 이상인지, 클릭 시 URL에 반영되는지까지만 검증하고
**순위의 정확성은 검증 대상에서 제외**했습니다. 설계서의 결과란도 비워 두었습니다.

### 3. 실행하지 않기로 한 것

**XSS (TC_004)** — 운영 중인 서비스에 공격성 입력을 실행하지 않았습니다.
스크립트는 작성해 설계 의도를 남기되 `skip`으로 두었습니다.

### 4. 테스트 대상이 사라진 것

```python
@pytest.mark.skip(reason="원티드에서 AI Agent 기능 제거됨 (2025.02.12)")
```

실제 서비스는 테스트 밑에서 바뀝니다. 삭제하지 않고 **사유와 날짜를 남겨** 기록으로 두었습니다.

## 💡 주요 기술 포인트

**1. BasePage — 공통 메서드 15개**
`find`, `click`, `wait`, `viewport` 조작 등 페이지 공통 동작을 추상화해 각 페이지 객체의 중복을 줄였습니다.

**2. 컴포넌트 단위 POM**
헤더는 특정 페이지에 속하지 않고 모든 페이지에 걸쳐 있습니다.
`header_component.py`로 분리해 여러 페이지 테스트에서 재사용합니다.

**3. 반응형 BVA — 경계값을 가정하지 않고 측정**

CSS 브레이크포인트 992px를 991px / 992px 두 케이스로 검증합니다.

다만 **`set_window_size()`는 창 전체 크기(스크롤바·테두리 포함)이고 CSS 미디어쿼리는 뷰포트 기준**이라
두 값 사이에 약 16px 차이가 납니다. 창을 992px로 맞춰도 실제 뷰포트는 경계 아래입니다.

창 크기를 조금씩 바꿔가며 **메뉴 표시가 실제로 전환되는 지점을 측정**한 뒤,
그 값을 기준으로 보정했습니다. 경계값 테스트에서 기준값 자체를 의심해야 한다는 걸 여기서 배웠습니다.

**4. 동적 스크롤 처리**
긴 드롭다운(지역 필터 3단계)과 긴 페이지(채용 상세)에서 요소를 찾기 위해
반복 스크롤 로직(`scroll_and_find`)을 구현했습니다.

**5. 봇 탐지 관련 Chrome 설정**
실제 서비스 대상이라 로컬 실행에서도 자동화 탐지에 걸렸습니다.
`--disable-blink-features=AutomationControlled`, `excludeSwitches` 등으로 `navigator.webdriver`를
드러내지 않게 설정했습니다. **로컬 실행이 가능한 수준까지만이고, 캡차 우회는 하지 않았습니다**
(아래 [CI/CD](#-cicd--구축-과정과-한계) 참고).

## 🔍 테스트 과정에서 겪은 문제

> 제품 측 결함으로 기록할 만한 이슈는 현재 없습니다.
> 아래는 **테스트 구현·환경 쪽에서 겪은 문제**입니다.

| ID | 문제 | 분류 | 원인 | 해결 |
|----|------|------|------|------|
| TR-001 | 1200px에서도 햄버거 메뉴가 보임 | 테스트 구현 | Locator가 숨김 처리 대상이 아닌 요소를 지정 | 디버깅용 테스트로 DOM 계층을 따라 올라가 숨김 대상을 특정, `button[data-gnb-kind='more']`로 교체 |
| TR-002 | Locator 수정 후에도 경계값에서 결과 불일치 | 테스트 환경 | `set_window_size()`(창)와 미디어쿼리(뷰포트)의 약 16px 차이 | 전환 지점을 직접 측정해 뷰포트 기준으로 보정 |

> TR-001·TR-002 모두 **처음에는 제품 결함으로 의심했던 건**입니다.
> 원인을 끝까지 따라가고 나서야 테스트 쪽 문제라는 것을 알았습니다.
> 테스트 실패를 제품 문제로 단정하지 않는 습관은 이 두 건에서 얻었습니다.

## 🔄 CI/CD — 구축 과정과 한계

GitHub Actions로 파이프라인을 구성했습니다.
**로컬에서 되던 것이 CI에서는 되지 않았고, 원인을 하나씩 분리해 해결했습니다.**

| 증상 | 원인 | 해결 |
|---|---|---|
| 테스트를 찾지 못함 | 러너의 작업 디렉터리는 레포 루트 | 실행 경로를 `01_automation_testing/tests/`로 수정 |
| Chrome 실행 실패 | 컨테이너 환경 제약 | `--no-sandbox`, `--disable-dev-shm-usage` 추가 |
| 드라이버 없음 | 러너에 ChromeDriver 미설치 | `ChromeDriverManager`로 런타임 설치 |

여기까지 해결한 뒤에도 실패가 남았고, **로그만으로는 원인이 보이지 않았습니다.**
스크린샷을 저장해 artifact로 함께 올려 화면을 직접 확인했고, **캡차가 걸려 있었습니다.**

대상이 남의 운영 서비스이므로 **캡차 우회는 하지 않기로 했습니다.**
파이프라인을 되돌리는 대신 아래로 정리했습니다.

- 실행 단계에 `|| true` — 캡차로 인한 실패에 워크플로가 멈추지 않도록
- 리포트·스크린샷은 `if: always()`로 계속 업로드 — 결과는 확인할 수 있도록

### 남은 한계

`|| true` 때문에 **워크플로는 어떤 실패에도 초록입니다.**
캡차로 인한 실패와 실제 회귀를 구분하지 못합니다. 당시에는 캡차를 피할 수 없다는 판단에서
파이프라인을 살리는 쪽을 택했지만, 지금이라면 **캡차를 감지해 skip으로 처리하고
그 외 실패는 그대로 드러나게** 하거나, CI 범위를 외부 서비스에 의존하지 않는 부분으로 좁혔을 것입니다.

스크린샷도 디버깅 목적으로 넣은 코드가 그대로 남아 있습니다 —
매 테스트 종료 시 같은 파일명으로 저장되어 마지막 한 장만 남습니다.

> 이 경험은 다음 프로젝트([Portfolio-Website](https://github.com/LimJaeSub/Portfolio-Website))에서
> **"안전망이 실제로 실패를 잡는지 먼저 확인한다"**는 원칙으로 이어졌습니다.
> 일부러 실패하는 테스트를 넣어 CI가 그것을 숨기지 않는지 검증하는 단계를 두었습니다.
